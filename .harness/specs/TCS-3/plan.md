## Design (decided here, not by the builder)

### GET /v1/events
- Params:
  - `since`: non-negative integer, default 0. Not an integer → 400 `{error}`.
  - `limit`: integer, default 50. Above 100 → 100. Below 1 → 1. Not an integer → 400. (Ticket: "limit=500 is clamped to 100".)
  - `ecosystem`, `component`: CSV. Trim each item, drop empty items, dedupe. Max 20 items each; more → 400 (keeps bind params under D1's 100 cap).
  - `min_severity`: one of `critical|high|medium|low`. Becomes `severity_label IN (<labels at or above>)`. `unknown` is never included. Any other value → 400.
  - `exploited`: only `true` is accepted and becomes `exploited = 1`. Any other value → 400.
- SQL (built by `buildEventsQuery`): `SELECT cursor, doc_json FROM advisories WHERE cursor > ? [AND ecosystem IN (...)] [AND component IN (...)] [AND severity_label IN (...)] [AND exploited = 1] ORDER BY cursor LIMIT <limit+1>`. Select only the 2 columns the response needs.
- Response: `{ events: Advisory[], next_cursor, has_more }`. `events` = `JSON.parse(doc_json)` of the first `limit` rows. `has_more` = more than `limit` rows came back. `next_cursor` = cursor of the last returned row; on an empty page, `next_cursor = since` (the client keeps its place).
- Headers: `Content-Type: application/json; charset=utf-8`, `Cache-Control: public, max-age=60`, strong `ETag`.
- ETag: `"` + first 32 hex chars of SHA-256 over the canonical JSON of `{ max: next_cursor, has_more, since, limit, ecosystem[], component[], min_severity, exploited }` (arrays sorted) + `"`. `has_more` is in the hash so a page whose rows are unchanged but whose `has_more` flipped does not answer 304.
- `If-None-Match`: split on commas, trim, strip `W/`, compare with the strong value (RFC 9110 weak comparison for If-None-Match). A hit → 304 with no body, with `ETag` and `Cache-Control`. `*` is not special-cased.
- Statement count: 1 D1 statement for the events query + 1 for the settings read in the rate limiter (see below). 2 total.

### GET /v1/events/:id and GET /v1/events/cve/:cve
- `:id`: `SELECT doc_json FROM advisories WHERE id = ?` (PK). Miss → 404 `{ "error": "not found" }`.
- `:cve`: uppercase, match `^CVE-\d{4}-\d{4,}$` else 400. `SELECT doc_json FROM advisories WHERE cve_primary = ? ORDER BY cursor LIMIT 1` (index `idx_advisories_cve_primary`). Miss → 404 `{error}`.
- Hono matches `/cve/:cve` (2 segments) and `/:id` (1 segment) separately; register `/cve/:cve` first anyway.

### Cross-cutting
- CORS: `hono/cors` with `origin: "*"`, `allowMethods: ["GET", "HEAD", "OPTIONS"]`, `exposeHeaders: ["ETag", "Retry-After"]`, mounted app-wide in `src/app.ts`.

### Rate limit (src/middleware/ratelimit.ts), mounted on `/v1/events` and `/v1/events/*`
- Key: `rl:v1:<ip>:<window>` where `ip = CF-Connecting-IP` (fallback `unknown`) and `window = floor(now / 60000)`. Stored in the existing `CURSORS` KV namespace with the `rl:` prefix (no new binding, so no operator step).
- Read the limit and the counter in parallel: `Promise.all([getSettingInt(DB, "feed.anon_rate_per_minute", 60), KV.get(key)])`.
- If `count >= limit` → 429 `{ "error": "rate limited" }`, `Retry-After: <seconds to window end, min 1>`, `Cache-Control: no-store`. No KV write on a refused request.
- Else `await KV.put(key, String(count + 1), { expirationTtl: 120 })` and continue. A KV put error is caught, logged as `{lane:"ratelimit", err}` and the request continues (fail-open: a counter fault must not take the public feed down). The settings read failing falls back to 60 and logs once per request.
- Fallback constant 60 is documented as the fallback only (CLAUDE.md rule 5); the live value is the `settings` row.

### Migration 0003_settings.sql (additive only)
```sql
CREATE TABLE IF NOT EXISTS settings (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL,
  updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%SZ','now'))
);
INSERT OR IGNORE INTO settings (key, value) VALUES ('feed.anon_rate_per_minute', '60');
-- Feed filtered by exploited: WHERE exploited = 1 AND cursor > ? ORDER BY cursor.
CREATE INDEX IF NOT EXISTS idx_advisories_exploited_cursor ON advisories (exploited, cursor);
-- Feed filtered by min_severity: WHERE severity_label IN (...) AND cursor > ? ORDER BY cursor.
CREATE INDEX IF NOT EXISTS idx_advisories_severity_cursor ON advisories (severity_label, cursor);
```
The PK index serves `WHERE key = ?`. No DROP, no RENAME. D1 has no RLS; the RLS law applies to Supabase only.

Planner check run during planning (python sqlite3 on 0001 + these 2 indexes, 2,000 rows):
- no filter → `SEARCH advisories USING INDEX idx_advisories_cursor (cursor>?)`
- `ecosystem IN (?)` → `USING INDEX idx_advisories_ecosystem_cursor (ecosystem=? AND cursor>?)`, no temp B-tree
- `exploited = 1` → `USING INDEX idx_advisories_exploited_cursor`
- `severity_label IN (?,?)` → `USING INDEX idx_advisories_severity_cursor` + `TEMP B-TREE FOR ORDER BY`
- `component IN (?)` → `USING INDEX idx_advisories_component_ecosystem` + temp B-tree
- multi-value `ecosystem IN (?,?)` → index + temp B-tree (see NOTE in invariants)

## System invariants
(a) Cross-run state: the rate-limit counter lives in KV key `rl:v1:<ip>:<minute>`, TTL 120 s. KV is eventually consistent across PoPs and allows about 1 write/s per key, so the counter is approximate under bursts; a failed put is fail-open by design (the public feed stays up). This is the spec's chosen store ("ETag + rate limit in KV"). The limit value lives in `settings` (PK `key`). No dedup/watermark state is added.
(b) External side effects: none metered. The only write is the KV counter put: success → counter +1 then serve; put failure → log + serve; settings read failure → fallback 60 + log. A 429 performs no write. No email, NVD or LLM call.
(c) Adversarial negatives for the 304 decision (a 304 hides data, so a false hit is client-visible): must NOT 304 when (1) the filters differ, (2) `since` differs, (3) `limit` differs, (4) a new matching row arrived (max cursor changed), (5) `has_more` flipped with the same max cursor, (6) `If-None-Match` is a different ETag or a list without ours, (7) no `If-None-Match`. Must 304 when the header holds our ETag alone, in a list, or with a `W/` prefix. Tests cover (1), (4), (5), (6), (7) and the list/`W/` hits.
   Rate-limit negatives: a different IP is not counted against the first IP; a request in the next minute window is not refused; health and discovery are never refused.
(d) Neighbors: #2 ingest writes `advisories.cursor` and uses the `CURSORS` KV for ingest cursors (keys without the `rl:` prefix: no overlap). #8 adds `plans`; it may move the rate limit into a plan row later (additive). The cron lane (`*/10`) does not read `settings` or `rl:` keys. NOTE: a multi-value `ecosystem`/`component`/`min_severity` filter sorts its matched set in a temp B-tree (planner output above); bounded by the matched set, not a full-table scan. A per-ecosystem UNION is the follow-up if a key screen measures slow.

Performance (BH-6946): reads per events request = settings read + KV get (parallel, `Promise.all`), then 1 D1 query. Expected statement count: 2 D1 statements. Indexes: listed per filter above. No screen, so no loading skeleton. Payload bound: 100 events per page.
